# FAQ 03 · 决策讨论点（内部参考，不对外发）

> **⚠️ 内部文件**：用于内部决策讨论、向上汇报、新人 onboarding 时讲背景。**不要发给客户、不要进客户邮件**。

## 1. 为什么自研而不用 Canal / Debezium

> 问的场景：管理层评估技术选型、新人质疑"为什么不用成熟开源方案"。

事实层依据：

| 维度 | 自研 (Sync-Data) | Canal/Debezium |
|---|---|---|
| 文件 + 行原子一致性 | **原生** | 不支持 |
| 多 client_id 隔离（每 client 独立目标库 + bucket） | **原生** | 弱（多 connector 配） |
| 客户端**就在源端机房** + 本地块队列 | **是** | 不分客户端 / 中心化 |
| 弱网 / 断网续传 | **磁盘块队列** | 依赖 Kafka 缓冲 |
| 服务端可远程调速 | **是** | 弱 |
| 需要 binlog 权限 | **不需要** | 必需 |
| 部署组件复杂度 | 2 个 binary | Kafka stack |

**关键 trade-off**：放弃了 binlog 工具的"近实时（秒级）"特性，换来对**文件 + 关联行复合一致性**、**多客户端强隔离**、**弱网友好**的支持。

**何时考虑切换 binlog 方案**：
- 延迟要求 < 10s
- 不再有文件场景
- 源数据库切到 PG / Oracle
- 单源数据量 > 1 TB/天

详见 [reference/06-competitive-landscape.md](../reference/06-competitive-landscape.md)。

## 2. 当前技术债（不对外）

按优先级排：

### P0 · 影响稳定性的

1. **`processed_blocks.json` 全量加载到内存**：随累积量增大，重启时间会变长。设想用 BoltDB / RocksDB 替换。
2. **服务端单点**：没有 HA。生产 3 周内有过 1 次因目标基础设施宕机连带告警的情况。设想加主备切换。
3. **`schemacache` 缓存失效**：DDL 频繁变动场景下可能短时间不一致。v3.3 在加 30min TTL + flush API。
4. **块上传失败的 audit trail 较弱**：死信目录只存块，**没有完整的失败原因 + 重试时间线**。

### P1 · 用起来不顺手的

1. **admin Web 写得粗糙**：功能够用，UI/UX 一般。是临时实现，没有专门做。
2. **pacing 修改没有审计日志**：谁改了什么，啥时候改的，看不到。
3. **错误码没标准化**：不同模块 `err=` 字段格式不一。v3.3 错误分类器是在 fix 这个。
4. **观测性不够**：没有完整的 Prometheus + Grafana。
5. **测试覆盖率有空白**：sender / scanner 关键路径有 unit test，integration test 偏弱。

### P2 · 用户侧能感知的

1. **删除不同步**：源端 DELETE 不反映到目标端，业务方偶尔会问。
2. **列变更需要手动同步**：源端 ALTER 后要去目标库执行。
3. **不支持 row 级幂等**：只能 block 级，如果一个 block 内部行重复推会重复 INSERT（实际很少发生）。

## 3. 未公开的演进方向（在调研）

> 措辞一律弱：**设想 / 在调研 / 路线图**。

### v3.3（正在做）

- **Pull-based pacing**：客户端主动 pull 策略，不再依赖心跳响应推
- **错误分类器**：服务端根据错误类型自动调整客户端 pacing
- **隔离基础设施**：把不同 mode / 不同 client 的逻辑彻底分开

详见 [reference/08-roadmap.md · v3.3](../reference/08-roadmap.md#二在做in-progress)。

### v3.4+（在调研）

- **客户端 WAL**：blockstore 加 WAL，崩溃恢复更强
- **PostgreSQL 源支持**：当前只 MySQL
- **服务端 HA**：主备 / 共享 sync_state
- **审计日志**：admin 修改记录、pacing 变更历史
- **观测完整化**：内置 Prometheus + 仪表板模板

## 4. 内部知识 / 历史决策

### 为什么 V2 被推倒重写

V2 设计太复杂：
- Redis Stream 7.x 做事务级聚合
- 16 分片 / 64-slot V4 路由调度
- React + Vue 双前端
- PostgreSQL + MySQL 双目标支持

**问题**：
- 部署组件多 → 客户机房维护难
- 调试链路长 → 出问题排查时间倍数级增加
- 代码复杂度高 → 团队改起来心累

**V3 决定**：砍掉所有非必要中间件，二端单 binary，简单可控。3 周完成重构（commit `1dec55b` → `7b7dfeb`）。事实证明这个决定对：上线后 3 周稳定运行无非预期故障。

### 为什么选 gRPC 而不是 HTTP

- 文件块传输天然适合 streaming，HTTP/1.1 不支持
- proto schema 强约束，比 JSON / OpenAPI 维护成本低
- Go 生态 gRPC 工具链成熟

### 为什么 h2c 不直接 TLS

- 简化客户端配置（不用维护 CA 证书）
- TLS 由 Nginx 反代上层做，运维更熟
- 内网部署不必要 TLS

### 为什么每客户端独立目标库

- 数据合规：客户离开时整库导出 / 删除最简单
- 隔离：单客户端写错不影响别人
- 备份：可以按客户独立备份策略

## 5. 不对外的话术

| 场景 | 别说 | 应该说 |
|---|---|---|
| 客户问"你们用的什么开源框架" | "我们就是基于 Canal/Debezium 改的" | "我们自研的 Go gRPC 同步通道，针对多门店 + 文件场景做了优化" |
| 客户问"为什么有时候延迟分钟级" | "扫表机制就是这样" | "默认 2 分钟扫描周期，可调到 30 秒；如果业务需要秒级，可以单独评估" |
| 客户问"会不会有数据丢失" | "理论上不会" | "客户端本地块队列 + 服务端幂等去重双层保障，部署 3 周以来无丢数据案例" |
| 客户问"能不能保证准实时" | "可以" | "当前定位准实时（分钟级），如果业务确实需要秒级，需要换 binlog 方案，可以单独讨论" |
| 客户问"为什么会有积压" | "网络不行" | "客户端本地块队列设计就是为了应对网络波动，积压会随网络恢复自动追上" |
| 客户问"出问题能不能远程帮忙看" | "我们登录到你机器" | "通过中心的 admin 后台可以看到客户端状态、调整限速、远程开关同步，**不需要登录客户机器**" |

## 6. 内部 KPI / 关注点

仅做参考，不对外：

- **可用性**：客户端 SLA、服务端 SLA（当前没正式定）
- **延迟 P95**：从源端 createTime 到目标端可见 — 看 admin 的 catchup 倍率
- **数据丢失事件数**：目前 0（自 V3.0 上线）
- **客户端日均同步量**：~150 MB / client
- **服务端单进程承载客户端数**：当前 10+，设计 50（max_connections）
